# Nura provisioning protocol

Status: PRD 2. Protocol version **1**.

> **Not yet exercised on hardware.** The robot has not been built, so every
> exchange described here has been verified only in software: the app's and the
> firmware's cryptography against published test vectors and against each
> other, and the whole flow against a simulated robot. Until a board runs it,
> treat this as the specification rather than as a description of something
> observed working.

This is the contract between the mobile app, the XIAO ESP32-S3 firmware and the
backend for first-time setup and Wi-Fi recovery. Every UUID, message layout,
state and error code used by any of the three lives here.

The constants are defined in code in exactly two places, which a test keeps
in step:

| Where                                                    | Language   |
| -------------------------------------------------------- | ---------- |
| `firmware/xiao_esp32s3/src/protocol.h`                   | C++        |
| `mobile/src/services/provisioning/protocol.ts`           | TypeScript |

`mobile/tests/provisioningProtocol.test.ts` parses `protocol.h` and fails if
the two disagree.

## 1. Overview

```text
User        App                    Robot (XIAO)              Backend
 |           |                         |                        |
 | Find Nura |                         |                        |
 |---------->| scan (service UUID)     |                        |
 |           |<------------------------| advertise "Nura-1B2C"  |
 | Select    |                         |                        |
 |---------->| connect, read DEVICE_INFO                        |
 |           |------------------------>| show 6-digit code      |
 | Types code|                         |                        |
 |---------->| SPAKE2 over PAIRING     |                        |
 |           |<----------------------->| verified               |
 |           | POST /devices/provisioning-sessions              |
 |           |------------------------------------------------->|
 |           |<-------------------------------------------------| token (10 min, single use)
 | SSID + pw |                         |                        |
 |---------->| WIFI_CONFIG (AES-GCM)   |                        |
 |           |------------------------>|                        |
 |           | COMMAND CONNECT_WIFI    |                        |
 |           |------------------------>| join Wi-Fi             |
 |           |<------------------------| STATUS notifications   |
 |           |                         | POST /devices/claim    |
 |           |                         |----------------------->|
 |           |                         |<-----------------------| device token
 |           |                         | POST /devices/heartbeat|
 |           |                         |----------------------->|
 |           | GET session, GET device status (polling)         |
 |           |------------------------------------------------->|
 |           |<-------------------------------------------------| online
 |           | COMMAND FINISH          |                        |
 |           |------------------------>| stop advertising       |
 | Name it   | PATCH /devices/{id}, POST /devices/{id}/complete-setup
 |---------->|------------------------------------------------->|
 |           |                         | heartbeat -> introduce |
 |           |                         |<-----------------------|
 |           |                         | "Hi. I'm Nura."        |
 | Success   |                         |                        |
 |<----------|                         |                        |
```

Success is shown only once the **backend** has received a heartbeat from the
robot after the claim. Nothing the robot says over BLE can make the app report
success on its own.

## 2. Device identity

| Value              | Example             | Source                                               |
| ------------------ | ------------------- | ---------------------------------------------------- |
| `hardware_id`      | `NURA-3C84279A1B2C` | `NURA-` + the 12 hex digits of the ESP32-S3 factory MAC (eFuse). Pattern `^NURA-[0-9A-F]{12}$`. |
| short id           | `1B2C`              | Last four characters of `hardware_id`.               |
| BLE name           | `Nura-1B2C`         | Advertised in the scan response.                     |
| bootstrap secret   | 32 random bytes     | Generated by the robot's hardware RNG on first boot, kept in NVS namespace `nura_id`. |
| device token       | `ndt_…`             | Issued by the backend at claim; the robot's credential from then on. |

Nothing personal is ever advertised: no user name, email, SSID, account id or
health information.

### Prototype bootstrap trust (read this before production)

Production robots should carry a per-device credential written at manufacture
and registered with the backend beforehand. Prototype hardware has no such
step, so PRD 2 uses **trust on first claim**:

1. On first boot the robot generates a random 32-byte bootstrap secret and
   stores it in NVS. It is never displayed, advertised or logged.
2. At its first claim the robot sends the secret; the backend stores only its
   SHA-256 hash.
3. Every later claim for that `hardware_id` must present the same secret.

This stops a second board that copies a `hardware_id` from taking over an
existing device record. It does **not** prove a never-seen device is genuine
Nura hardware — that needs manufacturing provisioning, which is deferred.
There is no global secret compiled into the firmware.

A full flash erase destroys the secret, and the backend then refuses to let
that board reclaim its record. See "Development recovery" in
`firmware/xiao_esp32s3/README.md`.

## 3. GATT service

All UUIDs share one random base, varying only the last byte of the first group.

| Name          | UUID                                   | Properties     | Needs verification |
| ------------- | -------------------------------------- | -------------- | ------------------ |
| Service       | `3326ea00-822c-4b86-884f-74b2d9c77b2f` | —              | —                  |
| `DEVICE_INFO` | `3326ea01-822c-4b86-884f-74b2d9c77b2f` | read           | no                 |
| `PAIRING`     | `3326ea02-822c-4b86-884f-74b2d9c77b2f` | write, notify  | no                 |
| `WIFI_CONFIG` | `3326ea03-822c-4b86-884f-74b2d9c77b2f` | write          | **yes**            |
| `COMMAND`     | `3326ea04-822c-4b86-884f-74b2d9c77b2f` | write          | **yes**            |
| `STATUS`      | `3326ea05-822c-4b86-884f-74b2d9c77b2f` | read, notify   | no                 |

Compare UUIDs case-insensitively: Android reports them lower case, iOS upper
case.

**MTU.** `PAKE_RESPONSE` is 98 bytes. On Android the app requests an MTU of
247 immediately after connecting; iOS negotiates at least 185 by itself. A
link that cannot fit 98 bytes is reported as a connection failure.

**Advertising.** The 128-bit service UUID goes in the advertising packet and
the name in the scan response (together they exceed 31 bytes). The app scans
with a service-UUID filter **and** re-checks the UUID in each result, so an
unrelated device that happens to be named "Nura-…" is never listed.

### 3.1 `DEVICE_INFO` (read, UTF-8 JSON)

```json
{
  "protocol": 1,
  "hardware_id": "NURA-3C84279A1B2C",
  "model": "Nura",
  "firmware_version": "0.1.0",
  "provisioned": false,
  "registered": false
}
```

`provisioned` means working Wi-Fi credentials are stored. `registered` means
the robot holds a device token. The app refuses a `protocol` it does not know.

### 3.2 `PAIRING` (write + notify, binary)

The first byte is the message type.

| Type | Name              | Direction   | Layout                        | Length |
| ---- | ----------------- | ----------- | ----------------------------- | ------ |
| 0x01 | `PAKE_START`      | app → robot | `01` ‖ pA (65)                | 66     |
| 0x02 | `PAKE_RESPONSE`   | robot → app | `02` ‖ pB (65) ‖ cB (32)      | 98     |
| 0x03 | `PAKE_CONFIRM`    | app → robot | `03` ‖ cA (32)                | 33     |
| 0x04 | `PAIRING_RESULT`  | robot → app | `04` ‖ result (1)             | 2      |

| Result | Name                 | Meaning / robot behaviour                                   |
| ------ | -------------------- | ----------------------------------------------------------- |
| 0x00   | `VERIFIED`           | Provisioning writes are unlocked for this connection.       |
| 0x01   | `WRONG_CODE`         | `cA` did not verify. Counts as a failed attempt.            |
| 0x02   | `CODE_EXPIRED`       | The code was older than 120 s. A new code is now displayed. |
| 0x03   | `TOO_MANY_ATTEMPTS`  | Attempt limit reached (see below). The robot disconnects.   |
| 0x04   | `MALFORMED`          | Bad length, unknown type, or a point not on the curve.      |
| 0x05   | `NOT_PAIRING`        | The robot is not in pairing mode.                           |

### 3.3 `WIFI_CONFIG` (write, encrypted)

```text
01 ‖ nonce (12) ‖ ciphertext ‖ tag (16)          total ≤ 512 bytes
```

- Cipher: **AES-128-GCM**.
- Key: `HKDF-SHA256(salt = nil, IKM = Ke, info = "nura wifi config v1", L = 16)`,
  where `Ke` is the SPAKE2 session key from §4.
- Nonce: 12 random bytes, fresh for every write.
- Additional authenticated data: the byte `01` followed by the ASCII
  `hardware_id`, so a payload cannot be replayed at a different robot.
- Plaintext: UTF-8 JSON.

```json
{
  "ssid": "Home Network",
  "password": "correct horse battery staple",
  "provisioning_token": "npt_…",
  "api_base_url": "http://192.168.1.20:8000"
}
```

| Field                | Rule                                                        |
| -------------------- | ----------------------------------------------------------- |
| `ssid`               | 1–32 bytes of UTF-8.                                        |
| `password`           | 8–63 characters (WPA2/WPA3 Personal passphrase).            |
| `provisioning_token` | As returned by the backend. Never the user's login token.   |
| `api_base_url`       | As returned by the backend. `http://` is accepted only by firmware built with `NURA_ALLOW_INSECURE_HTTP`. |

A write before verification, or one that fails to decrypt or parse, produces
`STATUS = FAILED` with `NOT_VERIFIED` or `INVALID_PAYLOAD`. A good write
produces `RECEIVED_CREDENTIALS`. Credentials are held in RAM only until the
robot has actually joined that network — see §5.

### 3.4 `COMMAND` (write, 1 byte)

| Byte | Command         | Effect                                                               |
| ---- | --------------- | -------------------------------------------------------------------- |
| 0x01 | `CONNECT_WIFI`  | Join the network from the last `WIFI_CONFIG`, then claim and register. |
| 0x02 | `RETRY_WIFI`    | Try again with the same credentials (after a timeout, say).          |
| 0x03 | `CLEAR_WIFI`    | Erase stored Wi-Fi credentials. Identity and device token are kept.  |
| 0x04 | `FINISH`        | Setup is done: stop advertising and disconnect.                      |

Every command needs a verified connection.

### 3.5 `STATUS` (read + notify, 2 bytes)

```text
state (1) ‖ error (1)
```

| State | Name                    |
| ----- | ----------------------- |
| 0x00  | `WAITING`               |
| 0x01  | `VERIFIED`              |
| 0x02  | `RECEIVED_CREDENTIALS`  |
| 0x03  | `WIFI_CONNECTING`       |
| 0x04  | `WIFI_CONNECTED`        |
| 0x05  | `REGISTERING`           |
| 0x06  | `REGISTERED`            |
| 0x07  | `FAILED`                |

| Error | Name                    | What the app tells the user                                   |
| ----- | ----------------------- | ------------------------------------------------------------- |
| 0x00  | `NONE`                  | —                                                             |
| 0x01  | `WIFI_AUTH_FAILED`      | Check the password and try again.                             |
| 0x02  | `WIFI_NOT_FOUND`        | Nura couldn't see that network. It needs 2.4 GHz.             |
| 0x03  | `WIFI_TIMEOUT`          | The network didn't answer in time.                            |
| 0x04  | `WIFI_UNSUPPORTED`      | The network type isn't supported (e.g. WPA Enterprise).       |
| 0x05  | `BACKEND_UNREACHABLE`   | Nura joined Wi-Fi but couldn't reach Nura services.           |
| 0x06  | `REGISTRATION_REJECTED` | The setup session expired. Start again.                       |
| 0x07  | `ALREADY_CLAIMED`       | This Nura is already linked to another account.               |
| 0x08  | `IDENTITY_MISMATCH`     | This Nura's identity doesn't match our records.               |
| 0x09  | `INVALID_PAYLOAD`       | Something went wrong sending the Wi-Fi details. Try again.    |
| 0x0A  | `NOT_VERIFIED`          | Verify the device first.                                      |
| 0x0B  | `NO_CREDENTIALS`        | Enter Wi-Fi details first.                                    |
| 0xFF  | `UNKNOWN_ERROR`         | Something went wrong. Try again.                              |

Status notifications are **not** encrypted. They carry nothing sensitive, and
they are advisory: an attacker able to forge one could make the progress UI
wrong, but not make setup appear to succeed, because success comes from the
backend.

## 4. Verification: SPAKE2

BLE proximity does not prove the user picked the right robot, and a six-digit
code is far too small to protect a key exchange by itself — anyone who
captures a code-derived exchange can try all million codes offline in
seconds. The protocol therefore uses a **password-authenticated key
exchange**: the code the robot displays authenticates the exchange, and an
attacker gets exactly one guess per online attempt, with nothing to test
offline. This is the same approach Matter uses for commissioning over BLE.

No cryptography is invented here. The suite is
**SPAKE2-P256-SHA256-HKDF-HMAC from RFC 9382**, used unmodified and checked
against the RFC's test vectors on both sides.

| Parameter | Value                                                                   |
| --------- | ----------------------------------------------------------------------- |
| Group     | P-256; points in uncompressed SEC1 form (65 bytes)                      |
| M         | `02886e2f97ace46e55ba9dd7242579f2993b64e16ef3dcab95afd497333d8fa12f`    |
| N         | `03d8bbd6c639c62937b04d997f38c3770719c629d7014d49a24b4f98baa1292b49`    |
| A (app)   | ASCII `nura-app`                                                        |
| B (robot) | ASCII `hardware_id`                                                     |
| AAD       | ASCII `nura-provisioning-v1`                                            |

**Password to scalar.**

```text
w = OS2IP( SHA-512( "nura-pake-w-v1" ‖ len(B) ‖ B ‖ len(code) ‖ code ) ) mod n
```

`len` is the RFC's 8-byte little-endian length, and `code` is the six ASCII
digits. RFC 9382 recommends a memory-hard function here, to protect a stored
`w` if a server is breached. Nura never stores `w` — it lives for one attempt
and the code is replaced right after — so a plain hash is used, and the
security comes from the attempt limits below.

**Exchange** (exactly RFC 9382 §3.3 and §4):

```text
App:    x ← [1, n-1];  pA = x·G + w·M            → PAKE_START
Robot:  check pA on curve;  y ← [1, n-1];  pB = y·G + w·N
        K = y·(pA − w·M)
App:    check pB on curve;  K = x·(pB − w·N)

TT       = len(A)‖A ‖ len(B)‖B ‖ len(pA)‖pA ‖ len(pB)‖pB ‖ len(K)‖K ‖ len(w)‖w
Ke ‖ Ka  = SHA-256(TT)
KcA ‖ KcB = HKDF-SHA256(salt = nil, IKM = Ka, info = "ConfirmationKeys" ‖ AAD, L = 32)
cA = HMAC-SHA256(KcA, TT);   cB = HMAC-SHA256(KcB, TT)
```

`w` is encoded as a 32-byte big-endian integer in TT.

1. Robot → `PAKE_RESPONSE` (pB, cB).
2. App checks cB in constant time. A mismatch means the code was wrong; the
   app says so and does not send `PAKE_CONFIRM`.
3. App → `PAKE_CONFIRM` (cA). Robot checks cA in constant time, then sends
   `PAIRING_RESULT`.

Both sides wipe x or y, w, K and Ka once the exchange ends. Ke is kept only
for the life of the BLE connection.

### Code lifetime and attempt limits

| Rule                                   | Value                                   |
| -------------------------------------- | --------------------------------------- |
| Code                                   | 6 digits from the hardware RNG. Never a factory PIN. |
| Shown on                               | The robot's screen. With no screen fitted, a development build prints it to the serial log — developers only (PRD 2, section 20). |
| Generated                              | When a phone connects while in pairing mode. |
| Expires                                | 120 s after it was shown; a new one replaces it. |
| Failed attempts per connection         | 3, then `TOO_MANY_ATTEMPTS` and disconnect. |
| Failed attempts per pairing-mode window | 10, then the robot leaves pairing mode.  |
| After leaving pairing mode             | A deliberate action is needed to re-enter (§6). |

An attacker therefore gets at most 10 guesses at a one-in-a-million code per
physical action by the owner.

## 5. Robot state machine

Two explicit machines rather than a pile of booleans.

**Connectivity** (Wi-Fi and backend):

```text
UNPROVISIONED ──credentials──▶ CREDENTIALS_RECEIVED ──CONNECT_WIFI──▶ WIFI_CONNECTING
      ▲                                                                   │
      │ CLEAR_WIFI                                        joined │        │ failed
      │                                                          ▼        ▼
      │                                                 WIFI_CONNECTED   ERROR ── (retry / new credentials)
      │                                                          │
      │                                    token held? ─no──▶ BACKEND_REGISTERING
      │                                          │                     │ claimed
      │                                         yes                    ▼
      └──────────────────────────────────────────┴─────────────────▶ ONLINE (heartbeats)
```

**Pairing mode** (orthogonal — a robot can be ONLINE and in pairing mode at
once, which is how Wi-Fi is changed):

```text
OFF ──enter──▶ ADVERTISING ──phone connects──▶ CONNECTED (code shown) ──SPAKE2 ok──▶ VERIFIED
 ▲                  │                               │                                  │
 └── timeout / FINISH / attempt limit / disconnect ─┴──────────────────────────────────┘
```

Credential rule: a new SSID and password are written to NVS **only after the
robot has joined that network**. A typo never overwrites credentials that
work, so a failed Wi-Fi change leaves the robot on its old network.

## 6. Pairing mode

| Situation                             | Behaviour                                               |
| ------------------------------------- | ------------------------------------------------------- |
| First boot (no Wi-Fi stored)          | Enters pairing mode automatically and stays in it until set up. |
| Already set up                        | Not discoverable. Hold **BOOT** for 3 s to enter pairing mode. |
| Pairing-mode window (set-up robots)   | 5 minutes, extended while a phone is connected.         |
| After a successful claim              | `FINISH` ends it immediately; otherwise it closes 60 s later. |
| Hold **BOOT** for 10 s                | Factory reset (see below).                               |

**Factory reset** clears Wi-Fi credentials, the device token and local
settings. It keeps the bootstrap identity, so the robot can be claimed again,
and it touches nothing on the backend — no cloud data is deleted.

## 7. Backend endpoints

Full request and response shapes are in [the API reference](../api/README.md).

| Caller | Endpoint                                             | Purpose                                   |
| ------ | ---------------------------------------------------- | ----------------------------------------- |
| App    | `POST /api/v1/devices/provisioning-sessions`         | Short-lived, single-use token for one `hardware_id`. |
| App    | `GET /api/v1/devices/provisioning-sessions/{id}`     | Has the robot claimed yet? Used when BLE drops mid-setup. |
| Robot  | `POST /api/v1/devices/claim`                         | Exchange provisioning token + bootstrap secret for a device token. |
| Robot  | `POST /api/v1/devices/heartbeat`                     | "I'm online"; returns the next interval, any pending introduction, and whether there is a presentation to fetch (PRD 11). |
| App    | `GET /api/v1/devices`, `GET /api/v1/devices/{id}`    | The account's robots.                      |
| App    | `PATCH /api/v1/devices/{id}`                         | Rename.                                    |
| App    | `GET /api/v1/devices/{id}/status`                    | Online / offline / unknown, from heartbeats. |
| App    | `POST /api/v1/devices/{id}/complete-setup`           | Request the introduction; mark `robot_connected`. |

### Tokens

| Token              | Format           | Lifetime                         | Stored as        |
| ------------------ | ---------------- | -------------------------------- | ---------------- |
| Provisioning token | `npt_` + 43 chars | 10 minutes, consumed by one claim | SHA-256 hash     |
| Device token       | `ndt_` + 43 chars | Until the next claim of that robot | SHA-256 hash     |

Both are 256 bits from `secrets.token_urlsafe`. The user's own access token
never leaves the phone.

A claim whose response was lost can be retried with the same provisioning
token while it is unexpired, by the same robot presenting the same bootstrap
secret. The retry rotates the device token, so a stale one stops working.

### Claiming rules

| Device state                          | Claim by the session's account          |
| ------------------------------------- | --------------------------------------- |
| Never seen                            | Created and claimed.                    |
| Claimed by the same account           | Re-claimed: same record, new device token, name kept. |
| Claimed by another account            | `409 already_claimed`, both when the session is created and at claim. |
| Bootstrap secret doesn't match        | `403 identity_mismatch`.                |

Ownership transfer is not implemented; the rules above leave room for a later
"release" action that clears `claimed_by_account_id`.

### Online and offline

| Setting                     | Value |
| --------------------------- | ----- |
| Heartbeat interval          | 30 s  |
| Interval during setup (until the introduction is acknowledged, or 5 min after claim) | 5 s |
| Online threshold            | 90 s since the last heartbeat (three missed beats) |

`connection_status` is derived on every read from `last_seen_at`, never
stored, so it cannot go stale: `unknown` if the robot has never sent a
heartbeat, `online` within the threshold, `offline` beyond it. A claim alone
does not count — only a heartbeat sent with the new device token does.

## 8. Timeouts and retries

| Step                               | Rule                                              |
| ---------------------------------- | ------------------------------------------------- |
| BLE scan                           | 12 s, then "We couldn't find Nura". Retry is manual. |
| BLE connect                        | 10 s, one automatic retry.                        |
| Wi-Fi join (robot)                 | 20 s per attempt, 2 attempts. A wrong password is reported at once, not retried. |
| Claim (robot)                      | 3 attempts, backing off 2 s then 4 s; 10 s HTTP timeout. |
| Waiting for "online" (app)         | Polls every 2 s for up to 90 s after `CONNECT_WIFI`. |
| Heartbeat failure (robot)          | Keeps its normal interval; never floods.          |

If BLE drops **before** `CONNECT_WIFI`, the app returns to discovery. If it
drops **after**, the app does not declare failure: it keeps polling the
backend, because the robot may well be joining Wi-Fi.

## 9. Security assumptions

- The owner is physically present and can see the robot's screen. The code
  proves that; BLE range alone does not.
- The phone app and the backend are trusted. The robot accepts
  `api_base_url` from the verified app, which is why release firmware refuses
  plain `http://`.
- BLE link-layer pairing is **not** used. The OS pairing dialogs are
  inconsistent across Android vendors, and bonding would leave Nura in the
  phone's Bluetooth settings permanently. Confidentiality comes from SPAKE2 +
  AES-GCM at the application layer instead.
- Status notifications and `DEVICE_INFO` are readable by anyone nearby while
  in pairing mode. Neither contains personal data.
- Never logged anywhere: Wi-Fi passwords, the pairing code, SPAKE2 values,
  provisioning or device tokens, the bootstrap secret, user access tokens.
- No medical data crosses BLE at any point.
- Robot-to-backend traffic uses HTTPS in release builds. Local development
  over plain HTTP is allowed only by the `NURA_ALLOW_INSECURE_HTTP` build flag.

## 10. Not in protocol version 1

QR-code bootstrap, spoken pairing codes, ownership transfer, a real-time
command channel (ADR 0003 still leaves WebSockets vs MQTT open), and
manufacturing-time device credentials.

PRD 11 extended the heartbeat rather than adding a transport, which its
section 58 asks for: the response now also carries `presentation_pending`, and
the robot fetches the envelope with its own request. The flag and not the
payload — a heartbeat is retried and logged, and a medication name travelling
in one would eventually sit in a retry log. The full contract is
[the presentation protocol](presentation-protocol.md).

PRD 11's pairing code is still **this** protocol's. Its section 35 forbids a
second pairing mechanism, so the `setup_code` presentation type and the
`PAIRING_CODE` layout exist for the firmware's own dispatch and nothing in the
backend ever queues one: the code is generated on the robot and drawn by the
robot, over BLE, before any device record exists.
