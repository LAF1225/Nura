# ADR 0005 — BLE library, and how the pairing code protects setup

- **Status:** Accepted (PRD 2). Implemented, but not yet exercised on hardware.
- **Date:** 2026-09-21
- **Context:** PRD 2 — Robot Pairing, BLE Discovery & Wi-Fi Provisioning

## Context

PRD 2 needs the app to find a robot over BLE, prove it is *this* user's robot,
and hand it a Wi-Fi password. Two decisions follow from that: which BLE library
the app uses, and what protects the moment the password crosses the air.

## Decision 1: react-native-ble-manager

| Candidate | Outcome |
| --------- | ------- |
| **react-native-ble-manager 12.5** | **Chosen.** States plainly that RN 0.76+ runs on the New Architecture only, and was published this month. |
| react-native-ble-plx 3.5 | Rejected. Last published February 2026, and its README still describes RN 0.74 / Expo 51 with no mention of the New Architecture. |
| Espressif's unified provisioning (`wifi_provisioning`) | Rejected. It would bring its own protocol and its own mobile SDK, and its proof-of-possession is a fixed per-device string, not the expiring code PRD 2 section 16 asks for. |

React Native 0.86, which this app is on, runs the New Architecture only, so the
library's support for it is not a preference but a requirement.

It ships an Expo config plugin, which is what adds the Bluetooth permissions to
the Android manifest and the usage description to iOS. Nura declares
`neverForLocation`, so Android 12 and later ask for nothing location-related;
Android 11 and earlier still need the location permission, because the OS
refuses to scan without it.

One trap worth recording: `write()` defaults to `maxByteSize: 20` and silently
splits anything larger into separate ATT writes, which would break every
message boundary in the protocol. Nura always passes the full attribute length
so a single write is made.

## Decision 2: SPAKE2, rather than trusting the BLE link

The robot shows a six-digit code and the user types it into the app. The
question is what that code actually secures.

A six-digit code is about 20 bits. If it were used to derive a key directly, or
to authenticate an ordinary key exchange, anyone who recorded the exchange
could try all one million codes offline in seconds and then decrypt the Wi-Fi
password. So the code cannot be used that way.

**Nura runs SPAKE2 (RFC 9382, P256-SHA256-HKDF-HMAC), with the code as the
password.** A password-authenticated key exchange gives an attacker exactly one
guess per online attempt and nothing to test offline. Matter uses the same
approach for commissioning over BLE, for the same reason. The session key that
falls out of it encrypts the Wi-Fi payload with AES-128-GCM.

No cryptography is invented: the suite is used unmodified, and both
implementations are checked against the RFC's own test vectors —
`mobile/tests/spake2.test.ts` and
`firmware/xiao_esp32s3/test/test_crypto/`. A third vector, generated by the
app and pinned in both suites, proves the TypeScript and C++ sides agree byte
for byte.

The only Nura-specific part is deriving the scalar `w` from the code, which
mixes in the hardware id so a code shown by one robot is useless at another.
RFC 9382 recommends a memory-hard function there; Nura uses a plain hash
because `w` is never stored and the code is replaced moments later, so the
attempt limits are what does the work: three tries per connection, ten per
pairing window, then the robot stops advertising.

### Why not BLE's own pairing

Bluetooth's Passkey Entry would also give a six-digit code and a MITM-resistant
link, handled by the OS. It was rejected because:

- the pairing dialogs vary between Android vendors and are a well-known source
  of flakiness, and the app cannot tell a wrong code from a failed write;
- bonding leaves Nura in the phone's Bluetooth settings permanently, which is
  the opposite of "BLE is for setup and recovery only" (ADR 0003);
- PRD 2 section 14 wants the code entered in Nura's own UI, where the app can
  say what went wrong.

## Consequences

**Good**

- The Wi-Fi password is encrypted to the specific robot whose screen the user
  read, not merely to whatever answered the advertisement.
- Success never depends on the robot's word for it: the app waits for the
  backend to confirm a heartbeat (PRD 2, section 36).
- The protocol is implementation-independent — the firmware and the app share
  only the document and two constant files, kept in step by a test.

**Costs and risks**

- Two implementations of one protocol, in different languages, with the
  cross-vector test as the guard against drift.
- An elliptic-curve exchange on an ESP32-S3 takes long enough that it runs in
  the main loop rather than the BLE callback, to avoid stalling the radio task.
- **None of it has run on hardware.** The robot has not been built. The crypto
  is verified against vectors and the firmware compiles, but no BLE connection,
  Wi-Fi join or claim has ever happened on a real device.

## Alternatives for the code display

The robot is expected to have a screen. Until one exists, a development build
prints the code to the serial log, which is a developer-only fallback — PRD 2
section 20 rules out sending ordinary users to a serial monitor. A QR code on
the robot's base (PRD 2, section 17) remains the documented fallback for
hardware without a screen, and is not implemented.
