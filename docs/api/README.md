# Nura API reference

Base URL in local development: `http://localhost:8000`
(from a phone: `http://<your-computer-lan-ip>:8000`)

Interactive, always-current docs are generated by FastAPI at
<http://localhost:8000/docs>. This file covers the conventions and the
endpoints that exist at PRD 0.

## Conventions

**Versioning.** Application routes live under `/api/v1`. A future `/api/v2` can
run alongside it so older app builds keep working.

```text
/api/v1/users      (later PRD)
/api/v1/devices    (later PRD)
/api/v1/health     (later PRD — health records)
```

`GET /health` is deliberately *not* versioned: "is this process up?" does not
change shape between API versions.

**Case.** The wire format is `snake_case`. The mobile app converts to
`camelCase` in `src/services/api/system.ts`, so the rest of the app never sees
wire naming.

**Content type.** JSON in, JSON out.

**Errors.** FastAPI's standard shape:

```json
{ "detail": "..." }
```

The app maps status codes onto typed error kinds and shows its own wording; it
never displays a raw server message or exception. See
`src/services/api/errors.ts`.

| Status | App error kind | Meaning                        |
| ------ | -------------- | ------------------------------ |
| 401    | `unauthorized` | Not signed in                  |
| 403    | `unauthorized` | Signed in, not permitted       |
| 404    | `notFound`     | No such resource               |
| 400    | `validation`   | Malformed request              |
| 422    | `validation`   | Body failed validation         |
| 5xx    | `server`       | Server-side failure            |

Transport failures never reach the server, so they have no status code. The app
classifies them as `offline`, `unavailable` (reachable network, unreachable
backend), `timeout`, or `configuration` (no API URL set in the build).

## Endpoints

### `GET /health`

Liveness probe. The mobile app uses this for its development-only connection
indicator on Today.

It does **not** touch the database. A liveness probe that fails because of a
database blip would report the wrong thing. If a readiness check is needed
later, it gets its own endpoint.

**Response `200`**

```json
{
  "status": "ok",
  "service": "nura-api"
}
```

### `GET /api/v1/version`

Lets the app confirm what it is talking to, and whether it is too old to keep
running against it. The app compares its own version against
`minimum_app_version` and can prompt the user to update.

**Response `200`**

```json
{
  "api_version": "0.1.0",
  "minimum_app_version": "0.1.0"
}
```

Both values come from `backend/app/core/config.py`.

## Not implemented yet

No endpoint reads or writes `users`, `user_settings` or `devices`. The tables
and models exist; the routes arrive with the PRDs that need them.

Authentication is not wired up. There is no `Authorization` header handling,
and no endpoint requires a session. PRD 1 adds sign-in, at which point the API
client gains the header and this document gains an auth section.

## Rules for every future endpoint

These are not optional, and they exist because the data is medical:

1. **Never trust a client-supplied user id for authorisation.** The
   authenticated identity comes from the verified token. A request that names a
   user id does not thereby gain access to that user's data.
2. **Check entitlement per resource.** Confirm the authenticated user may see
   the specific record requested — not merely that they are signed in.
3. **Caregiver access requires an explicit granted permission record.** Never
   an implied relationship.
4. **Validate every body with a Pydantic model.** No hand-rolled parsing.
5. **HTTPS outside local development.**
6. **Never log tokens, passwords, medical records or conversation content.**
