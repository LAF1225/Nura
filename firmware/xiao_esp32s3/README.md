# Nura robot firmware — XIAO ESP32-S3

> **Nothing here has run on hardware.** The robot has not been built. The
> firmware compiles for all three environments and its cryptography is checked
> against published test vectors, but no BLE connection, Wi-Fi join, claim or
> heartbeat has ever happened on a real board.

Implements the robot half of
[the provisioning protocol](../../docs/device/provisioning-protocol.md):
advertise over BLE, show a six-digit code, verify the phone with SPAKE2,
receive Wi-Fi credentials encrypted to that session, join the network, claim
itself with the backend, then heartbeat.

## Hardware assumptions

The robot does not exist yet, so the default build assumes **a bare XIAO
ESP32-S3 with nothing attached**. It works: pairing runs, and the pairing code
goes to the serial log.

| Assumption | Status |
| ---------- | ------ |
| Seeed XIAO ESP32-S3 | From PRD 0. |
| BOOT button for pairing and reset | Present on every XIAO ESP32-S3. |
| 240×320 SPI TFT | Planned, not fitted. Driver chip unconfirmed — `board_config.h` assumes ILI9341, with ST7789 one flag away. |
| I2S amplifier and speaker | Planned, not fitted. Pins in `board_config.h` are placeholders. |

Every pin in `board_config.h` is a placeholder chosen so nothing collides.
**Check them against the real wiring before trusting the peripheral build.**

## Layout

```text
src/
├── main.cpp              boot, state machine, button, heartbeat timing
├── protocol.h            UUIDs, message types, enums, limits (shared with the app)
├── board_config.h        which hardware is fitted, and on which pins
├── device_identity.*     hardware id and the bootstrap credential
├── settings_store.*      NVS: Wi-Fi, backend URL, device token
├── spake2.*              RFC 9382 role B
├── secure_channel.*      AES-GCM Wi-Fi payload
├── ble_provisioning.*    the GATT service and pairing session
├── wifi_manager.*        joining, and why it failed
├── backend_client.*      claim and heartbeat
├── display.*             screen, or serial when none is fitted
├── audio.*               introduction, or a log line when no speaker is fitted
└── log.h                 structured serial logging
test/test_crypto/         on-device tests (never run)
```

## Build and flash

PlatformIO is installed in `firmware/.venv`:

```bash
python -m venv firmware/.venv
```

```bash
firmware/.venv/Scripts/pip install platformio
```

Build (no board needed):

```bash
cd firmware/xiao_esp32s3 && ../.venv/Scripts/pio run -e xiao_esp32s3
```

| Environment | What it is for |
| ----------- | -------------- |
| `xiao_esp32s3` | Development: allows a plain `http://` backend on your LAN, verbose logs. |
| `xiao_esp32s3_release` | Refuses `http://`, quiet logs. |
| `xiao_esp32s3_peripherals` | Development plus the display and audio drivers, so that code keeps compiling while the hardware does not exist. |

Flash a connected board and watch it:

```bash
cd firmware/xiao_esp32s3 && ../.venv/Scripts/pio run -e xiao_esp32s3 -t upload
```

```bash
cd firmware/xiao_esp32s3 && ../.venv/Scripts/pio device monitor -b 115200
```

If the board is not detected, hold **BOOT**, tap **RESET**, release **BOOT** to
enter the bootloader, then add `--upload-port COMx`.

## Tests

They run **on the board**, because they exercise mbedTLS as ESP-IDF builds it:

```bash
cd firmware/xiao_esp32s3 && ../.venv/Scripts/pio test -e xiao_esp32s3
```

They check SPAKE2 against RFC 9382's vector, and against a vector generated by
the app — the same one pinned in `mobile/tests/crossImplementation.test.ts` —
including decrypting a Wi-Fi payload the app produced. If those pass on real
hardware, the two implementations genuinely agree.

## What the robot does

| Situation | Behaviour |
| --------- | --------- |
| First boot, or setup never finished | Enters pairing mode and advertises as `Nura-XXXX` until it is set up. |
| Set up, powered on | Joins the stored Wi-Fi and heartbeats. Never advertises. |
| **BOOT held 3 s** | Pairing mode for 5 minutes: change Wi-Fi, or re-link. |
| **BOOT held 10 s** | Factory reset: clears Wi-Fi, the device token and local settings. Keeps the device identity. Touches nothing in the cloud. |
| Wi-Fi lost | Retries every 30 seconds, stays linked to the account. |
| Unlinked by the account | Drops its token and waits to be set up again. |

## Serial diagnostics (developers only)

Ordinary users are never sent here; the app's pairing help covers them
(PRD 2, section 20). A development build prints:

```text
[BOOT]  Nura firmware 0.1.0 starting
[ID]    hardware id NURA-3C84279A1B2C, credential present
[PAIR]  BLE advertising started as Nura-1B2C
[PAIR]  app connected
[PAIR]  development fallback -- pairing code is 482731
[PAIR]  verification accepted
[WIFI]  credentials received for network Home Network
[WIFI]  connecting to SSID Home Network (attempt 1)
[WIFI]  connected, ip 192.168.1.42
[CLOUD] registering device (attempt 1)
[CLOUD] registered as device 0f9c...
```

Never printed: the Wi-Fi password, the provisioning or device token, the
bootstrap credential, or any SPAKE2 value. The pairing code appears **only** in
builds with no display fitted, because otherwise there would be no way to see
it at all.

## Development recovery

The bootstrap credential is generated once and kept in the `nura_id` NVS
namespace. A factory reset keeps it. A **full flash erase destroys it**, and
the backend will then refuse to let that board reclaim its device record
(`identity_mismatch`), because from the backend's point of view a different
board is claiming a known hardware id.

If that happens during development, delete the device row so the robot can be
claimed fresh:

```bash
psql -U nura -h localhost -d nura_dev -c "DELETE FROM devices WHERE hardware_id = 'NURA-XXXXXXXXXXXX';"
```

A proper ownership-release endpoint is deferred (PRD 2, section 31).

## HTTPS

Release builds refuse a plain `http://` backend. They also refuse `https://`
unless a root certificate is compiled in, rather than skipping verification:

```ini
build_flags = -DNURA_BACKEND_ROOT_CA='"-----BEGIN CERTIFICATE-----\n..."'
```

Embedding ESP-IDF's full CA bundle would be the better answer for production
and is not done yet. The HTTPS path has never been exercised.
